# Выпуск и канал обновлений

1. Выполнить `scripts/build.ps1 -Version <версия>` и `scripts/package.ps1 -SkipBuild -Version <версия>`. Официальная подпись требует закрытого ключа издателя из защищённого локального хранилища. Ключ не публикуется. Для независимой сборки используется `-NoReleaseSignature`.
2. Проверить подпись, контрольные суммы, содержимое MSI и исходников. В архиве не должно быть ключей, пользовательских настроек или журналов.
3. Публиковать кандидаты как предварительные GitHub Releases. Рядом с MSI разместить `release.json`, `release.sig`, `SHA256SUMS.txt`, исходники оболочки и соответствующие исходники сторонних компонентов.
4. Запустить `Windows installer lifecycle` в GitHub Actions с тегами двух тестовых выпусков. Он проверяет настоящий MSI, остановку/запуск службы, намеренный сбой после инициализации, откат данных и прав службы, успешное обновление и удаление. Результаты на Windows Server не заменяют матрицу Windows 10/11.
5. Завершить проверки из [VALIDATION.md](VALIDATION.md), включая обновление через приложение от обычного пользователя. Сохранить отчёт с указанием проверенного SHA-256.
6. Для стабильного канала использовать **точный тег `v<версия>`**, например `v2.0.1`. Встроенный клиент получает манифест через `releases/latest/download`, а MSI — из `releases/download/v<версия>/`. Простого снятия отметки prerelease с тега `v2.0.0-preview.2` недостаточно.

Опубликованный подписанный пакет не заменять другими байтами под тем же тегом. Исправления предварительных сборок получают новый тег; неподходящий выпуск отзывается. После стабильного выпуска исправления получают новый номер версии. Для пользователей установленной 2.0.0 следующая автоматически предлагаемая версия должна быть выше 2.0.0.

Скрипты фиксируют версии и контрольные суммы внешних компонентов. Поддерживается повторная сборка из исходников; совпадение MSI байт в байт между отдельными сборками пока не подтверждено.
